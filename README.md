# Nearry

React Native + Expo SDK 54, with Personal and Business experiences and Supabase Auth, Postgres, Storage and Realtime. The Everyday Nearby UI uses the Current Clay palette: warm-white surfaces, dark ink and one burnt-orange accent. Both account experiences share the same type, icons, controls, and safe-area-aware navigation.

## Run

Use Node 22+ and npm:

```sh
npm ci
cp .env.example .env
python3 -m pip install pillow
npm run assets
npx expo start
```

Set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` to your project URL and public anon/publishable key. Restart/rebuild after changing values. Never include a service-role key or push worker secret in `EXPO_PUBLIC_*` variables.

Use `npm run web` for the browser preview, or scan the Expo QR code / use a development build on your phone. The browser build uses React Navigation as a single-page app.

The welcome screen offers separate Personal and Business demos. Real operations with an unconfigured backend fail clearly. Demo changes are in memory and reset on reload; they are not proof of live integration.

For a native Google login test, use a development/standalone build with the `nearry` custom scheme, rather than relying on Expo Go redirects. Icons are generated by `assets/generate_icons.py` before native prebuild (the APK workflow does this).

## Backend installation / upgrade

Follow [migration instructions](supabase/migrations/README.md). New installs use migrations `00001`–`00025`; existing installations apply only missing migrations. `run-all.sql` is fresh-database-only and refuses to run when profiles already exist. No production database is automatically modified by the application or CI.

Migrations `00011`–`00018` introduce required RPCs, so deploy migrations and the matching app version together. Older app versions relying on raw join/booking writes will need to update.

## Authentication

- Email uses a six-digit OTP. Enable the Supabase Email provider and include `{{ .Token }}` in the Magic Link template (and signup template if used). Configure custom SMTP for real recipients.
- Log in uses `shouldCreateUser: false`; Sign up allows account creation. Neither asks for passwords or phone numbers.
- Google uses Supabase OAuth with explicit PKCE. Enable Google using a Google Cloud Web OAuth client and the callback URL displayed by Supabase. Keep the Google secret only in Supabase.
- Allow-list `nearry://auth/callback` in Supabase Auth redirects. For web, add your exact `/auth/callback` URL and configure hosting to serve the app at that path.
- The app exchanges callbacks, restores Supabase sessions, and loads the private owner profile through `get_my_profile()`.
- A first-time Google user confirms Personal or Business before onboarding. Returning accounts retain their selected type. Profile fetch failures show a retry screen; stale results cannot restore another account after sign-out.

## Real place search

Search and Nearby's location picker support Geoapify suggestions through an authenticated Supabase function. Choose a location to see Nearry activity within 5 km, or use it as the Nearby feed's center. Required provider attribution appears beside results. See [place search setup and provider migration](docs/place-search.md) for the server-only API key, migration `00019`, usage limits, deployment and the future Google adapter contract.

## Protected flows

- Join requests use `request_join`, `approve_join_request`, `decline_join_request` and `withdraw_join_request`. Direct client request mutations are denied. Operations lock the post first and enforce caller identity, capacity and expiry. Counts expose aggregate numbers while request rows remain private.
- Upcoming full activities can still be cancelled by the host; accepted participants can leave a full activity. Withdrawal only reopens eligible fill-closed posts.
- Businesses define a booking window, duration, resource name and capacity. Slots are generated on the server; customers select a slot ID. Direct booking writes and customer self-confirmation are denied.
- New pending bookings hold seats for up to 30 minutes. The business confirms through `change_booking_status`; expired/cancelled bookings cannot be revived. Cancellation releases capacity. Existing legacy bookings keep their original timestamps and allocations.
- Business verification is a private image upload plus `submit_verification` RPC and a durable review queue. See [server setup](supabase/functions/README.md) for the mail worker, signed review links, and scheduler. Approval and venue associations require a trusted administrator. Clients cannot change verification status or claim a venue directly.
- Profile column grants expose only public identity fields. Onboarding, business details and verification-document paths are accessed through the owner-only profile RPC.
- Nearby supports manual area filtering and opt-in GPS within 5 km. Sample distances are labelled in demo mode.

## Push and realtime

Database notification events create `push_jobs`; the app does not submit arbitrary recipients or notification text to a push function.

Deploy `supabase/functions/send-push` as a scheduled worker:

```sh
supabase secrets set PUSH_DISPATCH_SECRET=YOUR_RANDOM_SERVER_SECRET
supabase functions deploy send-push --no-verify-jwt
```

Disabling JWT verification here is paired with the worker's required `x-dispatch-secret` check. Configure a trusted scheduler to POST to the function every minute using that header. Keep the header secret in server/scheduler configuration only. Hosted Supabase supplies the service role environment variables.

The worker claims up to 10 committed events, sends bounded Expo batches, records ticket errors, removes immediately rejected DeviceNotRegistered tokens and retries failures up to five claims. Delivery is at least once: a timeout after Expo accepts a batch can cause a retry/duplicate. Expo ticket acceptance is not proof of device delivery; receipt reconciliation is implemented in migration 00025; device-level delivery remains a release check.

Push registration reuses an existing notification permission rather than prompting on every startup. If permission has not been granted, users can tap Enable notifications in Profile/Business. Denied permissions can be changed in system settings. Registration and sign-out deregistration are serialized; a token belongs to the latest registered account. Sign-out displays an error if deregistration fails instead of silently leaving a token attached.

Migrations add relevant tables to `supabase_realtime` if that publication exists. Verify dashboard Realtime configuration and two-device updates in the target project.

Schedule server expiry jobs separately: `close_expired_posts()` and `expire_booking_holds()` every minute using a trusted service role.

## Account safety and privacy

See [account safety rollout](docs/account-safety-rollout.md) for migrations **00024 and 00025**, worker deployment, public privacy/support configuration and device checks. Both roles have Safety & privacy, report history, blocked people, notification preferences and confirmed account deletion. Reports are private; only a trusted service operator can moderate them. Blocking is enforced on the server and keeps existing bookings manageable. Deletion deactivates immediately, then a protected worker removes files before Auth and related records. The app includes an 18+ community-terms acknowledgement; account deletion remains accessible without agreement. Set the actual legal operator and monitored support email before releasing or exporting public policies with `npm run legal:export`.

The push worker stores accepted per-device tickets and checks receipts. Notifications contain generic text and a recipient-checked notification ID. The app uses an explicit Expo project UUID. Deploy backend migrations and workers before distributing the matching app; schedules and live credentials are not configured by this repository.

## Tests and checks

```sh
npm run typecheck
npm test
npm run sql:check
npx expo install --check
npm run assets
EXPO_NO_CACHE=1 EXPO_NO_TELEMETRY=1 npx expo export --platform android --platform web
```

The committed tests run database authorization/functions/triggers in PGlite. Only PostGIS operations are stubbed in that embedded run. They exercise direct-write attacks, host/participant/outsider permissions, capacity, expiry, withdrawal, role selection, private profiles, notification ownership and token reassignment.

For full PostGIS and separate-connection concurrency checks, use a **fresh disposable** PostgreSQL database named `nearry_test`:

```sh
TEST_DATABASE_URL=postgres://postgres:password@localhost:5432/nearry_test npm run test:database
```

The suite creates test schemas and roles; never point it at a real project. CI runs this against a disposable PostGIS service, including simultaneous last-spot approvals and bookings. A committed lockfile and `npm ci` make checks repeatable.

Before rollout, test Google/OTP delivery, app restart, both account types, denied location permission, proof upload, a three-account join journey, bookings, chat and notifications on real devices. No README claim substitutes for a live test. Payments and a full administrator dashboard remain outside this milestone; business proof review uses the protected email review page.

## Backend audit

See [audit scope, fixes, and remaining live checks](docs/backend-audit.md). Offer editing/publishing/cancellation now uses `update_offer`; cancelling an offer also cancels its future reservations. Customers keep the offer context in booking history. Chat loads the newest 200 messages, merges concurrent send/realtime results, and acknowledges only displayed messages while the conversation is focused. Older-message pagination remains future work.

Search treats punctuation and pattern characters as literal text, and keeps expiry and text conditions together. Optional post fields can be explicitly cleared. Badges refresh after local read actions; chat and notification lists refresh on incoming events and app resume. Remote push is owned by the server worker, avoiding duplicate local banners from the same database event.

## Dependency maintenance

Expo SDK 54 / React Native 0.81 target Android API 36 with the New Architecture and edge-to-edge layout. Native packages follow Expo's supported versions. Photo/document uploads retain the compatible filesystem API, and foreground notifications use the banner/list API. CI compiles an unsigned native release and checks its manifest, permissions and 16 KB native alignment. This does not replace a signed release test on a phone. See [Android release setup](docs/android-release.md) for signing, environment variables and the first Play internal test. Do not use `npm audit fix --force` to change the framework blindly.

## Everyday Nearby · Current Clay design

- Palette: warm white `#FAF9F5`, ink `#252A26`, burnt orange `#C14D2F`. Statuses use explicit text, with no extra brand colours.
- Typography: Avenir Next on iOS, the system sans elsewhere; comfortable body text and medium-weight headlines. Native text scaling is retained.
- Discovery: an illustrated Play / Meet / Explore / Unwind grid, original clay artwork, and larger rounded Plan / Place / Offer cards. Existing detail screens handle joining and booking; opening a card never submits a request. Offer cover photos use business uploads; illustrated venue covers are explicitly labelled as an overview.
- Nearby: category tiles filter the feed and bring it into view; tap the selected tile or Show all to reset. A horizontal featured rail uses the loaded, area-scoped live offers, preferring those marked spotlight. Its controls never auto-advance. When there are no offers, an invitation starts the real Create flow. Search, attribution, area selection, refresh and realtime updates retain their existing services.
- Venue pages: cover/gallery photos, community rating (never labelled as Google), directions, actual amenities, live venue offers and plans, a full-screen photo viewer, and a bottom action that scrolls to available times/plans or starts a new plan. Absent photos/amenities/ratings have honest empty states. Directions open an external map search and need no map API key.
- Layout: warm paper, raised ivory cards, dark ink and one burnt-orange accent; an uncluttered location header and a rounded dark-ink tab bar. All five tabs remain labelled, with height and bottom space reserved for device insets and scaled labels. The bar stays in normal layout, so content cannot slide underneath it.
- Motion: `MotionProvider` observes the device's Reduce Motion preference. Presses use a short scale spring; screens enter with a 240 ms fade/lift; native stacks slide and the photo viewer fades. Reduce Motion disables these effects and animated scrolling. There are no looping decorative animations. The existing business verification welcome also respects this setting. Test native gestures and keyboard on a phone before release.
- Original artwork and the built-in image-generation prompt are documented in `assets/discovery/README.md`. The shared transparent atlas is bundled once; it is category illustration, not real venue photography.
- Feed thumbnails use twelve distinct activity miniatures (including football, badminton, cricket, coffee, chess, food, kayaking, cycling, movies, music and wellness), separate from the larger home scenes. Titles, details and tags choose relevant artwork; a post's first uploaded photo takes precedence. Create Post accepts up to five JPEG/PNG/WebP images, 10 MB each. Post details show the gallery and full-screen viewing. Failed photo saves remain retryable against the saved post, with no new post created on retry. See [photo setup and verification](docs/post-photos.md).
- Personal messages: the header chat icon on Nearby, Search, Create, Activity and Profile opens Your conversations. Its badge shows unread messages (hidden at zero, capped at 99+ visually) and shares the tab navigator's unread snapshot. Opening the inbox alone does not mark chats read; the existing conversation screen acknowledges displayed messages. Headers use the existing Messages → Conversation routes and Supabase chat services. Business users retain their Messages tab.
- Personal listings: Profile → My posts (also linked from Activity) includes every post you created, even with no join requests. Filter All, Upcoming, Past or Cancelled; open a row to manage requests, edit or cancel an eligible post. The list refreshes on return, on live post/request changes and when pulled down. No additional database setup is needed.
- Shared pieces live in `src/components`; palette/type tokens live in `src/theme`. Reuse `DiscoveryCard`, `DiscoverySearch`, `VenueRow`, `PostRow`, `OfferRow`, `BrandHeader`, `PageHeading` and `FilterTabs` instead of adding another screen-specific design.
- Nearby area controls open from the header. GPS alone enables the “Within 5 km” label; demo and unfiltered results are labelled honestly. Interest buttons filter plans, offers and places; All restores the complete feed.
- Search uses the data services in both real and explicit demo modes. Stale requests cannot replace a newer query, and offers open their real detail route.
- The Business dashboard counts bookings in the local calendar day, excludes cancelled bookings, and labels live offers accurately. A confirmation failure is shown instead of silently ignored.
- Demo data uses valid local timestamps and associated venue IDs. Demo bookings use stable slots and their actual capacity. Live bookings send the selected slot ID to `book_offer_slot` instead of substituting the current timestamp. Demo mutations remain in memory.

Review on a phone with both a short and a long display name. Check Nearby filters, the area picker, Search, details, Create, keyboard dismissal, Activity, and Profile; then check all five Business tabs. Verify the native safe areas and large-text setting on iOS and Android before release. Browser checks are useful for layout, but cannot verify native Google redirects, push permission, or device keyboard behavior.
