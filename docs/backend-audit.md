# Backend functionality audit

This branch audits the existing MVP services and forward database migrations, building on the Hello Nearry UI branch. It does not connect to or modify the deployed Supabase project.

## Reproduced and fixed

| Area                     | Failure                                                                                                                  | Change and evidence                                                                                                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Proof submission         | Required an undeclared `pg_net` extension and a hard-coded project URL; the transaction failed without it                | Migration `00018` queues private jobs. Database regression submits proof without `pg_net`.                                                                                                                                         |
| Verification delivery    | A public endpoint accepted an arbitrary user ID and could repeatedly send a private document                             | Secret-authenticated bounded worker reads server-owned jobs; email links to private proof instead of attaching it. Server configuration is documented.                                                                             |
| Verification decisions   | GET links could approve; missing expiry was accepted; old links could approve a later proof; write errors were ignored   | Signed tokens require a finite expiry and bind a review job, owner and document. GET only displays; explicit POST uses an atomic service-only RPC. HTTP, token and database tests cover these cases.                               |
| Offer publishing/editing | Direct updates used a conflicting lock order compared with bookings                                                      | Owner-only `update_offer` locks business then offer. Raw updates and protected patch keys are denied; services use the RPC.                                                                                                        |
| Offer windows            | Windows shorter than one slot created no bookable times                                                                  | Server and client validation enforce at least one complete slot.                                                                                                                                                                   |
| Offer cancellation       | Future reservations remained active and could block the same resource                                                    | Cancelling/ending cancels pending and future confirmed bookings transactionally, using existing customer notifications. Migration also reconciles future bookings on already-cancelled offers. Past confirmed history is retained. |
| Booking history          | Cancelled offers vanished through RLS, losing title/business/chat context                                                | Customers can read the public offer row linked to their own bookings; unrelated accounts still cannot read it.                                                                                                                     |
| Slot availability        | RPC could show expired/unverified offers and occupied overlapping legacy resources                                       | Availability now follows the reservation visibility and resource-conflict rules.                                                                                                                                                   |
| Venue association        | New offers omitted a business's reviewed venue and disappeared from location-filtered discovery                          | New offers inherit the first reviewed venue; selecting another business's venue is denied. Venue ownership still needs administrative review.                                                                                      |
| Discovery                | Raw punctuation could break REST filters; expiry used an unreliable literal and separate OR clauses                      | One combined filter, explicit ISO timestamp, quoted values, escaped literal regex patterns, safe tag arrays. Real supabase-js HTTP serialization is regression-tested.                                                             |
| Editing posts            | Clearing an optional cost sent no update; zero cost appeared empty                                                       | Explicit null clears optional fields; zero remains visible. HTTP-boundary regression checks clearing.                                                                                                                              |
| Chat history             | Ascending limit returned the oldest 200 messages                                                                         | Newest page is fetched descending, then displayed chronologically. Older-history pagination is not implemented.                                                                                                                    |
| Chat reads               | Hidden mounted conversations could mark unseen messages read; new arrivals between fetch/read were acknowledged          | Focus-scoped subscription, stale-request guards and a read RPC through the last displayed message only. Database tests retain later messages as unread.                                                                            |
| Chat chronology          | Clients could supply forged future timestamps/read watermarks                                                            | Message insert column grants and server timestamps; read writes only through membership-checked RPCs.                                                                                                                              |
| Chat duplicates          | Send response and realtime reload could add/replace the same message                                                     | Merge by ID with chronological ordering; regression covers overlapping snapshots.                                                                                                                                                  |
| Notifications            | Join resubmission reused a row without notifying; local badges lagged; local and remote delivery could duplicate banners | Pending transition notifies again, read actions emit refresh events, lists refresh on inserts/resume, server owns push delivery. Exact unread counts avoid the REST row limit.                                                     |
| Notification page        | No visible back action and failures marking read were silent                                                             | Back action, live refresh, stale-request protection and clear failure feedback.                                                                                                                                                    |
| OAuth/session            | Consumed web callback codes remained in the URL; pending role could hydrate too late                                     | Callback parameters are removed after exchange, and hydration waits for stored role restoration. Native/live provider checks remain below.                                                                                         |
| Proof upload             | PNG bytes were labelled JPEG; web used a native-only file read; failed submissions left unused uploads                   | Detect actual image format, use browser reads on web, upload with correct MIME and no overwrite, clean up after rejected submission. Pure tests cover format/size guards.                                                          |
| Demo behavior            | Requests ignored capacity/expiry and leaving did not reopen a full post                                                  | Demo guards/count updates align with core flow; cancellation releases future demo reservations and chat contexts remain separate. Demo remains memory-only.                                                                        |

The audit also reviewed email OTP options, role selection/onboarding, private profile grants, authorization on joins/bookings/chat, cancellation and expiry, notification ownership, push-token reassignment, location queries, and service error propagation. Redundant client push calls were removed because delivery is queued by database events.

## Automated validation

- Local suite: 47 passing tests; three separate-connection concurrency checks require disposable PostgreSQL and are skipped in PGlite.
- TypeScript and generated SQL consistency checks pass.
- Android and web production bundles export successfully.
- CI runs the same database authorization tests against a disposable PostGIS database, including simultaneous last-spot operations, offer cancellation versus reservation, competing review decisions, and distinct job leases. The PR check is the source of truth for that run.
- Verification HTTP tests execute the actual review handler with a fake database boundary. No email, push or private proof is sent externally during tests.

## Deployment and remaining live checks

1. Review [migration instructions](../supabase/migrations/README.md), back up the existing project, and apply only missing migrations through `00018`. For a project at `00016`, only `00017` and `00018` are new. They require the matching app build. The cancelled-offer reconciliation changes future reservation statuses; review that effect before rollout.
2. Deploy both updated verification functions and the existing push worker using [server setup](../supabase/functions/README.md). Configure secrets, a permitted mail sender, and trusted schedules. Old emailed tokens are invalidated. Pending proofs are backfilled for new delivery.
3. In staging, run two Personal accounts plus a Business account through email/Google, onboarding, app restart/sign-out, proof review/resubmission, venue association, offer creation/publishing, joining/approval/leaving, capacity races, booking hold/confirmation/cancellation, chat and notification reads.
4. On physical iOS/Android devices verify callback redirects, foreground/background reconnect, image picking, denied/granted GPS and notification permissions, and push delivery. Browser bundles and database tests cannot verify these platform integrations.

Limits remain: no older-message pagination, no Expo receipt reconciliation, no payment integration or full admin dashboard. Email and push are at-least-once delivery; provider acceptance does not prove recipient/device delivery. Existing Expo SDK 52 dependency advisories need a separate supported SDK upgrade. Production credentials, dashboard configuration, deployed function versions, SMTP/Google settings, live mail/push, native devices, and production data were not verified in this audit.
