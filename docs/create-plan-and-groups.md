# Create Plan and plan groups

The personal Create/Edit Plan screen follows the seven Downloads references: numbered cards, an activity grid and title suggestions, local quick dates, time/duration, the existing Google/registered venue/manual-coordinate picker, people counter, gender, level, adult age range, Free/Split/Per person, photos and a live preview. The footer remains outside scrolling content. Host approval and public plan discovery stay explicit. Recurring plans, follower-only visibility and automatic waitlist promotion are not presented as working controls: those need separate product/backend flows. Existing waiting requests still return to Pending when a full upcoming plan reopens.

Preferences round-trip through `plan_details`; actual ages remain private profile fields. Gender and age eligibility are enforced by the server for both requests and approvals. After people are approved, the age range can only be widened, avoiding exclusions or probing members’ private ages. Level is a self-selected guide. Duration is informational. Split fee stores the total and shows an estimate for the host plus the requested number of people; it does not collect payments or promise the same share when fewer people attend. Existing photo-save retry and ownership checks remain.

Each new plan receives one group in its creation transaction. Migration 00036 backfills one group per existing plan. Membership is derived from the host and approved join requests; there is no independently editable roster. Pending, full/waiting, declined and withdrawn requests do not grant access. Approval adds access immediately, including existing approved members. A host can rename their group; later plan-title edits preserve that custom name.

A participant can leave from the group or existing plan/activity flow. Both use the same locked withdrawal RPC, so the approved count falls once, the displayed available spots increase, and a full future plan reopens unless its deadline/start passed. Repeated leave is safe. Hosts cancel their plan instead of leaving it orphaned. A cancelled plan’s group is read-only. Removing/deactivating accounts and plans retains existing commitments/deletion protections; group tables cascade through their parent records. No account reset is performed.

Messages has a separate Plan groups section; plan details also links to the group. Messages page in batches of 60, up to 500 displayed, while the inbox shows the latest 200 groups. Group sends are limited to 30 messages per sender per minute across groups. Retries use a stable client key, so a lost response cannot duplicate a message or its notices. Read markers acknowledge a displayed message sequence and never mark later messages read. Notification links open the correct group, badges count messages once, and the existing push outbox sends generic lock-screen text. Realtime is mounted only for the focused group and foreground/focus refresh rechecks access. Private history is unavailable to outsiders and immediately revoked on withdrawal; blocked/inactive members and removed messages are filtered by the database. Members can report messages and people, block people, and use the existing moderation queue.

## Rollout

1. Apply only `supabase/migrations/00036_plan_groups_and_editor.sql` to the linked project, once. The generated `supabase/run-all.sql` is for fresh installs, not an existing project.
2. Deploy the updated `send-push` function if using its generic “new message” wording. The existing push worker still receives only notification IDs in device payloads; it never sends private message text to Expo.
3. Install the new app build after merging the PR. Older app builds continue to create plans, which also receive groups through the server trigger; their default preferences are empty.

Phone checks: create a photo plan and verify preview, keyboard, crop and failed-upload retry; edit and reload all preferences; host A and member B request/approve and see the same group; pending C cannot enter; exchange messages and verify unread/push links; rename as A; leave as B while a full plan reopens; re-request/approve and rejoin; cancel and verify read-only; report/block and confirm lost access. Test a retry on poor connectivity and Android/iOS keyboard visibility. Local database tests cover permissions, existing-member backfill, capacity, notices, reads, moderation, preferences and concurrent last-slot operations (the concurrency case requires the disposable PostGIS test database).
